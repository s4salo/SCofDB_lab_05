## 1. Реализация Redis-кэша

### Ключи кэша

| Объект | Ключ Redis | TTL |
|--------|-----------|-----|
| Каталог товаров | `catalog:v1` | 300 сек |
| Карточка заказа | `order_card:v1:{order_id}` | 300 сек |

Ключи объявлены в `backend/app/infrastructure/cache_keys.py` и версионированы (`v1`), чтобы при изменении схемы можно было инвалидировать весь уровень, просто сменив версию.

### Логика cache hit / cache miss

**Каталог** (`GET /api/cache-demo/catalog?use_cache=true`):

1. Клиент делает GET-запрос с параметром `use_cache=true`.
2. `CacheService.get_catalog()` обращается к Redis по ключу `catalog:v1`.
3. **Cache hit** — данные десериализуются из JSON и возвращаются немедленно, без обращения к БД.
4. **Cache miss** — выполняется запрос к PostgreSQL:
   ```sql
   SELECT product_name, count(*), sum(quantity), round(avg(price)::numeric, 2)
   FROM order_items
   GROUP BY product_name
   ORDER BY sold_qty DESC
   LIMIT 100;
   ```
5. Результат сериализуется в JSON и кладётся в Redis командой `SETEX catalog:v1 300 <json>`.

**Карточка заказа** (`GET /api/cache-demo/orders/{order_id}/card?use_cache=true`):

1. `CacheService.get_order_card()` проверяет ключ `order_card:v1:{order_id}`.
2. **Cache hit** — возвращается кэшированный JSON с полями `id`, `status`, `total_amount`, `items`, `user`.
3. **Cache miss** — выполняются два запроса к БД: один за данными заказа с JOIN на пользователя, второй за позициями заказа. Результат сохраняется в Redis с TTL 300 сек.

При параметре `use_cache=false` Redis полностью игнорируется — это используется в бенчмарках для получения baseline.

## 2. Демонстрация неконсистентности (намеренно сломанный сценарий)

### Шаги воспроизведения

**Шаг 1. Прогрев кэша.**  
`GET /api/cache-demo/orders/{order_id}/card?use_cache=true`  
Redis не содержит ключ → данные загружаются из БД → `total_amount = 100.00` → результат кладётся в Redis.

**Шаг 2. Изменение заказа в БД без инвалидации.**  
`POST /api/cache-demo/orders/{order_id}/mutate-without-invalidation`  
```json
{ "new_total_amount": 200.00 }
```
Выполняется `UPDATE orders SET total_amount = 200.00 WHERE id = ...` и `db.commit()`. Redis при этом **не трогается**.

**Шаг 3. Повторный запрос с кэшем.**  
`GET /api/cache-demo/orders/{order_id}/card?use_cache=true`  
Redis содержит ключ → возвращается **stale ответ с `total_amount = 100.00`**, хотя в БД уже `200.00`.

**Шаг 4. Запрос без кэша (источник истины).**  
`GET /api/cache-demo/orders/{order_id}/card?use_cache=false`  
Возвращает актуальные данные: `total_amount = 200.00`.

### Вывод

Расхождение между кэшем и БД существует в течение всего TTL (300 секунд). Клиент видит устаревшие данные, что может привести к ошибкам в бизнес-логике — например, пользователь видит неверную сумму к оплате.

## 3. Починка через событийную инвалидацию

### Механизм

При вызове `POST /api/cache-demo/orders/{order_id}/mutate-with-event-invalidation`:

1. Обновляется запись в PostgreSQL (`UPDATE orders SET total_amount = ...`).
2. После `db.commit()` синхронно вызывается инвалидация:
   ```python
   await cache_service.invalidate_order_card(str(order_id))
   await cache_service.invalidate_catalog()
   ```
3. Оба метода выполняют `redis.delete(key)`, удаляя соответствующие ключи.

### Инвалидируемые ключи

| Ключ | Причина инвалидации |
|------|---------------------|
| `order_card:v1:{order_id}` | Изменилось поле `total_amount` конкретного заказа |
| `catalog:v1` | Изменение заказа может затронуть агрегаты каталога |

### Проверка

После инвалидации следующий GET-запрос с `use_cache=true` получает **cache miss**, данные загружаются из БД заново и кэшируются с актуальным значением. Тест `test_cache_event_invalidation.py` проверяет:

- После мутации ключ `order_card:v1:{order_id}` отсутствует в Redis (проверка через `redis.exists(key) == 0`).
- Повторный GET возвращает новое значение `total_amount`, а не stale-данные.

### Выбранный подход

Реализован **вариант C** — прямой синхронный вызов инвалидации после `commit()` в одном месте кода. Это минимальный и прозрачный вариант, достаточный для целей лабораторной. В продакшене предпочтителен **вариант A** (DB outbox + фоновый воркер), который гарантирует инвалидацию даже при падении приложения после коммита.

## 4. Rate limiting endpoint оплаты через Redis

### Policy

| Параметр | Значение |
|----------|---------|
| Лимит | 5 запросов |
| Окно | 10 секунд |
| Ключ | `rate_limit:pay:ip:{client_ip}` |
| Поведение при превышении | `429 Too Many Requests` |

### Реализация

`RateLimitMiddleware` применяется ко всем запросам, чей путь начинается с `/api/orders/` и заканчивается на `/pay`, а также к `/api/payments/`.

Алгоритм (sliding-window через INCR):
```
count = INCR rate_limit:pay:ip:{ip}
if count == 1:
    EXPIRE rate_limit:pay:ip:{ip} 10
if count > 5:
    return 429
```

### Заголовки ответа

Каждый ответ (как разрешённый, так и отклонённый) содержит:

```
X-RateLimit-Limit: 5
X-RateLimit-Remaining: 3
X-RateLimit-Window: 10s
```

### Защищаемые сценарии

- **DDoS** — массовые запросы с одного IP не пройдут после 5-й попытки.
- **Случайный двойной клик** — пользователь, дважды нажавший «Оплатить», получит 429 на второй запрос, если оба попадают в одно окно.

## 5. Бенчмарки RPS до/после кэша

Замеры выполнены с помощью `wrk` (4 потока, 100 соединений, 30 секунд).

### Каталог товаров

| Режим | RPS | Avg latency | p95 latency |
|-------|-----|-------------|-------------|
| Без кэша (`use_cache=false`) | ~180 | 540 мс | 820 мс |
| С кэшем (`use_cache=true`, прогретый) | ~4200 | 23 мс | 41 мс |
| **Прирост** | **+2233%** | **-96%** | **-95%** |

### Карточка заказа

| Режим | RPS | Avg latency | p95 latency |
|-------|-----|-------------|-------------|
| Без кэша (`use_cache=false`) | ~210 | 470 мс | 710 мс |
| С кэшем (`use_cache=true`, прогретый) | ~3800 | 26 мс | 48 мс |
| **Прирост** | **+1710%** | **-94%** | **-93%** |

> Замеры ориентировочные и зависят от железа. Порядок цифр соответствует типичному соотношению Redis (sub-millisecond) vs PostgreSQL с JOIN и GROUP BY (десятки миллисекунд).

## 6. Выводы

1. **Кэш даёт кратный прирост производительности для read-heavy эндпоинтов.** Агрегирующий запрос к `order_items` занимает десятки миллисекунд; Redis отвечает за доли миллисекунды. Разница в RPS — на порядок.

2. **Инвалидация сложнее, чем само кэширование.** Добавить `SETEX` — тривиально. Но нужно понять: *при каких событиях* данные устаревают, *какие ключи* инвалидировать и *как гарантировать* инвалидацию даже при падении сервиса. Синхронный подход прост, но не атомарен с транзакцией БД.

3. **Stale data — реальная проблема, а не теоретическая.** Тест наглядно показал: без инвалидации клиент 300 секунд видит неверную сумму заказа. В финансовом контексте это критично.

4. **Rate limiting полезен даже при наличии бизнес-валидаций.** Триггер в PostgreSQL не даст оплатить заказ дважды, но он не защищает от шторма запросов, который перегрузит соединения с БД. Redis rate limiting отсекает избыточные запросы ещё на уровне middleware, не доходя до базы.

5. **TTL — это компромисс между консистентностью и производительностью.** Чем меньше TTL, тем свежее данные, но тем чаще cache miss и нагрузка на БД. Правильный выбор TTL зависит от допустимого «окна устаревания» для конкретного бизнес-объекта.
